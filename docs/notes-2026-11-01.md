## Running it locally

- `pnpm dev`, then open http://localhost:4321. The website is at `/` and the app at `/app/`. The app's own dev server runs on port 5173 behind it; if something else is already using 5173 (an older `pnpm dev`), it stops with an error instead of quietly moving to another port. Stop the old one with Ctrl+C first.
- `pnpm build` makes `dist/` (website at `/`, app at `/app/`), the exact files Cloudflare serves.
- `pnpm dev:api` builds everything and runs the Worker locally at http://localhost:8787, so the Feedback button works too (feedback is only logged locally, not emailed).

## Deploying to Cloudflare

- The Worker `megacsv` exists on the Cloudflare account; it was first deployed on Oct 31, 2026 (UTC). It's not attached to megacsv.com yet, so it's only at `megacsv.<subdomain>.workers.dev`.
- Deploy from the Mac: `pnpm run deploy` (builds everything, then `wrangler deploy`). Pushing to GitHub doesn't deploy, because the repo isn't connected to Cloudflare. If it gets connected later, Cloudflare's build machine needs Rust to build the engine.
- Deploy with the config in `worker/wrangler.jsonc`. A deploy replaces anything changed by hand in the dashboard, so make dashboard changes in that file instead.
- Logs are on (`observability` in `wrangler.jsonc`).
- Still to do: attach megacsv.com (a `routes` entry with `custom_domain: true`), then submit the sitemap to Google Search Console and Bing.

## Feedback email

- Sent **from** `hi@megacsv.com` (`FEEDBACK_FROM`, same as set in the dashboard; the binding only allows that sender).
- Sent **to** `FEEDBACK_TO`, a Wrangler secret. It must be a *verified destination address* in Email Routing, meaning the real inbox that `hi@megacsv.com` forwards to, not `hi@megacsv.com` itself. Without paid Email Sending, a Worker can only send to verified destination inboxes (Cloudflare Email Service docs, "Limits").
- Set it once, then deploy and send a test from the Feedback button:
  ```
  cd worker
  npx wrangler secret put FEEDBACK_TO
  pnpm run deploy
  ```
- Until it's set, the Feedback button on the live site fails.

## "Try a sample file"

- On the homepage and in the app. The browser makes up 16 MB of realistic transactions and repeats it into a 2 GB file of 27.5 million rows (`app/src/sample.ts`; the link is `/app/?sample`).
- Nothing is downloaded or stored on our side. It's the same file every time, so instant reopen works on it too.
- From clicking the button on the homepage to rows on screen: 0.8 s, page load included. All rows read in 2.2 s.
- Public sample files from other sites were ruled out: the app may not request other sites (CLAUDE.md rule 5), most such sites block it, and a multi-GB download would hide our speed.

## Speed measurements

Measured Nov 1, 2026 on a MacBook Air (M1, 8 GB RAM) in Chrome, with test files from `pnpm gen` (order rows, 12 columns). Raw results: `logs/measure-1gb.log`, `logs/measure-big.log`.

| | 1 GB | 5 GB | 20 GB |
|---|---|---|---|
| Rows | 9,732,075 | 48,273,484 | 191,964,560 |
| First rows on screen | under 0.1 s | 0.1 s | under 0.1 s |
| Every row read | 1.3 s | 5.1 s | 20.2 s |
| Find a word | 2.1 s | 5.4 s | 24.0 s |
| Filter (country is IN) | 1.6 s | 8.9 s | 43.0 s |
| Export the filtered rows to CSV | 4.2 s | 19.3 s | 82.9 s |
| Open it again later | 0.1 s | 0.1 s | 0.1 s |

**What the homepage shows (owner decision):** big numbers alone can look slow, so speed is only shown next to something worse.

- The bar chart "Seconds until you see your data": first rows in 0.1 s and all rows in 5.1 s, against 33 minutes to upload the same 5 GB to a cloud tool at 20 Mbps. The 33 minutes is arithmetic (5 GB at 20 Mbps is 2,000 s), not a measurement.
- "Excel stops at 1,048,576 rows, about 2% of that file."
- A "Side by side" table: all 48,273,484 rows vs Excel's first 1,048,576; about 1 GB a second vs a 2.5 MB-a-second upload; reopen in 0.1 s vs Excel reading the whole file again; 20 GB tested vs Google Sheets' 10 million cells.
- Excel and Power Query timings were dropped: Excel isn't installed on the test Mac and Power Query is Windows-only. Add them only if someone times them on a real machine.
- The full table above is kept for a future "we timed it" blog post.

## Why a filter shows at most 5,000,000 rows

Seen on a filter that matched 5,499,648 rows: "Showing the first 5,000,000 of 5,499,648 matching rows. Export to get all of them."

- The filter itself is complete: it finds and counts every match, and **an export includes all of them**. Only the on-screen view stops at 5 million.
- **Why:** for each matching row, the view keeps three numbers in browser memory: where the row starts in the file, where it ends, and its true row number. That's 24 bytes per row (`VIEW_CAP` in `app/src/engine/query-run.ts`). 5 million rows is 120 MB, which is fine. But a filter on a 20 GB file can match 50–100 million rows, which would need 1.2–2.4 GB, and on an 8 GB laptop that can crash the tab.
- **The catch:** the limit also hits people whose result is only slightly over and whose computer could easily hold it.

**How to fix it (decision pending):**

1. **Recommended: keep the list of matching rows on disk.** The browser has private on-disk storage (OPFS) that the app already uses for instant reopen. The list would be written there, and the grid would read only the rows on screen, the same way the file itself is handled. Memory stays flat whether a filter matches 5 million rows or 500 million. It changes the filter engine, so it needs property tests (CLAUDE.md rule 8), but it removes the limit for good.
2. **Quick improvement:** store each match in 12 bytes instead of 24 (the end of a row can be found from its start) and raise the limit to about 10 million. The 5.5-million-row case above would fit, but a limit would remain.

Option 2 can ship first if something is needed sooner.
